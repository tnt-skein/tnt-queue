# Очередь заданий

`tnt-queue` — надёжная очередь заданий Tarantool. Сообщение лежит
в спейсе и переживает перезапуск узла, а работники на файберах этого же
узла берут его и исполняют обработчик. Работа внутри — рок `queue`
1.5.0: очередь в спейсах, сроки, приоритет, ключ порядка. Пакет задаёт
договор поверх неё: конверт с опознавателем отправителя, подтверждение
итогом обработчика, зарытые в своём спейсе, контекст заголовками
сообщения, отправка частью транзакции `box` и отказ парой `nil, err`.

```lua
local queue = require('tnt.queue')

local mail = queue.declare('mail', { ttr = 30 })

local consumer = mail:consume(function(message)
    local ok, reason = deliver(message.body)

    if not ok then
        return nil, reason              -- повтор с отсрочкой, потом зарыть
    end
end, { workers = 2 })

local sent, err = mail:send({ to = 'a@example.org' })
```

Гарантия — хотя бы раз: повтор приходит по `ttr` и после перезапуска,
и отсекает его получатель по опознавателю сообщения. Потеря бывает
только по сроку жизни `ttl`, и она считается.

Зависимости: рок `queue` 1.5.0-1 с `rocks.tarantool.org` (очередь
в спейсах; грузится лениво, при первом деле на узле для записи),
`tnt-message` (конверт, проверка настроек отправки и тела, приговор
обработчику, область обработчика, крюки и ряды метрик: отправлено,
обработано по итогу, ожидание, глубина — общая часть договора очереди),
[`tnt-must`](https://github.com/tnt-skein/tnt-must) (проверки
аргументов), [`tnt-clock`](https://github.com/tnt-skein/tnt-clock)
(время зарытого), [`tnt-id`](https://github.com/tnt-skein/tnt-id)
(опознаватель чужой задачи), [`tnt-log`](https://github.com/tnt-skein/tnt-log)
(журнал), [`tnt-storage`](https://github.com/tnt-skein/tnt-storage)
(отказ `TntStorageFailure`) и
[`tnt-external`](https://github.com/tnt-skein/tnt-external) (подмена
рока, сна и признаков узла в проверках). Остальное — `fiber` Tarantool.

## Зачем пакет

Работу, которую нельзя делать внутри запроса, — письмо, вызов чужого
сервиса, пересчёт, — ставят в очередь: запрос отвечает сразу, а работа
идёт отдельно и переживает сбой. Очередь в спейсе даёт то, чего нет
у брокера снаружи: отправка — часть транзакции `box`, и «сохранили заказ
и поставили письмо» — одна фиксация, без ящика исходящих.

Рок `queue` написан людьми, знающими файберы, и переписывать его
незачем. Но договор у него свой, и в десятке мест он молча теряет либо
отказывает не парой. Что закрывает пакет:

| У рока | В пакете |
|---|---|
| отказ — голый `nil` (вне `RUNNING`) или исключение | пара `nil, err` с `TntStorageFailure` |
| `take` вне `RUNNING` отдаёт пустоту сразу, и цикл получателя встаёт без уступки: 72 тысячи вызовов за 0,2 с, гигабайты журнала, `SIGTERM` не доходит | работник ждёт `RUNNING`: на узле для чтения — `box.ctl.wait_rw`, в окне подъёма — короткий сон |
| номер задачи — `max + 1`, и после опустошения трубы он снова 0 | опознаватель ставит отправитель: ULID `tnt-id` |
| `ttl` стирает и зарытое | зарытые — в своём спейсе `<имя>_dead` |
| `ttr` по умолчанию — сто лет, и задача умершего файбера висит взятой до перезапуска | `ttr` конечен всегда, умолчание 60 с |
| возврат без отсрочки теряет срок удаления: сообщение с `ttl` не истекает, а в получасовое окно раз в 213 суток любое выбрасывается сразу | срок пишется заново той же транзакцией |
| подтвердить можно только из взявшего файбера | взятие, обработчик и итог идут в одном файбере |
| безключевые задачи идут одной цепочкой под ключом `'nil'` | ключ по умолчанию — опознаватель сообщения |
| загрузка на узле для чтения подменяет вызов `box.cfg` и печатает стек в stdout | рок грузится лениво, только на узле для записи |
| числа выдач нет | `attempt` в конверте, запись сразу за взятием |
| `put`, бросивший посреди своей транзакции, оставляет её открытой | транзакция рока откатывается, чужая — остаётся вызывающему |

Пакет делает для этого пять вещей:

- **Подтверждение — итог обработчика**, а не вызов, который можно
  забыть: значение подтверждает, `nil, err` возвращает сообщение
  с отсрочкой, последняя попытка зарывает его до решения человека.
- **Зарытые живут в своём спейсе** и не исчезают по сроку: их видно,
  их можно вернуть на выдачу `kick`.
- **Отправка в транзакции — её часть.** Откат уносит и сообщение,
  а с `atomic` запись обработчика и подтверждение фиксируются вместе.
- **Контекст едет с сообщением.** Опознаватель запроса отправителя
  приходит в обработчик заголовком, и записи обработчика в журнале
  находятся по нему.
- **Крюки отправки и обработки** дают трассу и замеры, не делая пакет
  зависимым от трассировщика.

**Договор общий с шиной событий.** Конверт, итог обработчика и отказ
устроены так же, как у шины событий
[`tnt-event`](https://github.com/tnt-skein/tnt-event), и исполняет их
тот же код, пакет `tnt-message`: обработчик переезжает между ними без
правки, когда событию понадобится пережить перезапуск. Поэтому тело — только простые данные, а незнакомая
настройка — исключение, а не молчаливый пропуск.

Драйвер рока — всегда `utubettl`: он единственный умеет и ключ, и сроки,
а два драйвера под одним фасадом дали бы две очереди с разным
поведением.

## Как пользоваться

### Объявление: `declare`

`queue.declare(name, opts) → queue`.

```lua
local mail = queue.declare('mail', { ttr = 30 })
```

| Ключ | Что | Умолчание |
|---|---|---|
| `ttr` | сколько у обработчика на одно сообщение, секунды; больше 0 и меньше ста лет | 60 |
| `shape` | форма тела `tnt-data` — таблица с `from(body)`: проверяется при отправке и на входе получателя | нет |

Имя очереди — латинская буква, дальше латиница, цифры и подчёркивание:
им зовётся спейс трубы, а с приставкой `_dead` — спейс зарытых.
Объявление на узле для записи заводит оба спейса сразу; на узле для
чтения оно ничего не трогает, а труба заведётся при первом деле, когда
узел начнёт писать. Негодное имя и негодная настройка — исключение
на строке вызывающего:

```lua
queue.declare('_mail')
--> error: имя очереди — строка по образцу ^%a[%w_]*$, а не «_mail»

queue.declare('mail', { ttl = 600 })
--> error: настройки очереди: ключа «ttl» нет, есть shape, ttr
```

`ttr` объявляется у очереди, а не у сообщения: сколько идёт обработка,
знает тот, кто объявляет получателя. Обработчику, которому `ttr` мало,
лучше объявить очередь с большим `ttr`, чем надеяться на `touch`.

Форма `shape` — то, что даёт `data.define` пакета
[`tnt-data`](https://github.com/tnt-skein/tnt-data), либо любая таблица
с функцией `from(body) → value | nil, errors`. Тело не по форме —
исключение при отправке, а на входе получателя — зарытое сообщение:
вход из очереди недоверенный, его могла положить прежняя сборка
приложения.

```lua
local data = require('tnt.data')

local Letter = data.define({ name = 'Letter', fields = { { 'to', 'string', min = 3 } } })
local letters = queue.declare('letters', { shape = Letter })

letters:send({ to = 7 })
--> error: тело для очереди letters не по форме: to: должно быть строкой
--> длиной не меньше 3 знаков, а не 7
```

**Имя — одна очередь на процесс.** Очередь объявляют там, где она нужна:
отправитель — в одном пакете, получатель — в другом. Второе объявление
того же имени отдаёт ту же очередь, и у объявлений всё общее: счётчики
`status()`, получатели, сообщения в работе, которые продлевает `touch`,
и крюк рока, которым считается `expired`. Две очереди над одной трубой
разошлись бы: крюк у трубы рока один, и истёкшие считало бы последнее
объявление, `sent` и `ack` — каждое своё, а `touch` через соседнее
отказывал бы «не в работе».

```lua
local sender = queue.declare('mail', { ttr = 30 })      -- в пакете, который отправляет
local receiver = queue.declare('mail', { ttr = 30 })    -- в пакете, который обрабатывает

sender == receiver                      --> true
```

Поэтому и настройки у очереди одни: объявление с другим `ttr` или другой
формой — исключение на строке вызывающего. `ttr` сравнивается значением —
`declare('mail')` и `declare('mail', { ttr = 60 })` объявляют одно и то
же, — а форма — таблицей: объявлениям одной очереди нужна одна и та же
`data.define`, а не две одинаковые.

```lua
queue.declare('mail', { ttr = 60 })
--> error: очередь mail уже объявлена с ttr 30, а не 60

queue.declare('mail', { ttr = 30, shape = Letter })
--> error: очередь mail уже объявлена с другой формой тела
```

Объявление, которое бросило, — например, имя трубы занял чужой спейс, —
очередь не объявляет: следующее заводит её заново и вправе прийти
с другими настройками.

### Перечитывание кода: `reset`

`queue.reset()` забывает объявленные очереди и останавливает их
получателей. Нужен проверкам и перечитыванию кода: модуль, загруженный
заново, объявляет очередь ещё раз — бывает, с другим `ttr`, — и заводит
получателя, который иначе встал бы рядом с прежним, и сообщения брал бы
и прежний обработчик.

```lua
local mail = queue.declare('mail', { ttr = 30 })

queue.reset()

mail = queue.declare('mail', { ttr = 60 })    -- не исключение: прежнее объявление забыто
```

Трубы и сообщения остаются в спейсах, крюки — в списке пакета: их снимает
`queue.hook(имя, nil)`. Объявленная заново очередь считает с нуля
и забирает себе крюк рока, которым считается `expired`. Очередь, взятая
до `reset`, отправляет дальше, но счёт у неё свой, а её получатели
остановлены: взятое дорабатывают, нового не берут.

### Отправка: `send`

`queue:send(body, opts) → id | nil, err`. Опознаватель — ULID, и он
тот же у повторной выдачи: по нему получатель отсекает повтор.

```lua
local id, err = mail:send({ to = 'a@example.org' }, {
    key = 'a@example.org',              -- порядок внутри ключа
    delay = 5,                          -- не выдавать раньше пяти секунд
    ttl = 600,                          -- через десять минут выбросить и сосчитать
    priority = 0,                       -- 0 — первым
    headers = { ['x-tenant'] = 'acme' },
})
```

| Ключ | Что |
|---|---|
| `headers` | свои заголовки поверх перенесённых контекстом; имена строчные, значения — строки |
| `key` | ключ порядка: сообщения одного ключа выдаются по одному |
| `delay` | не выдавать раньше срока, секунды; от 0 до ста лет |
| `ttl` | сколько сообщение живёт в очереди с отправки, секунды; истекло — выброс со счётом |
| `priority` | порядок выдачи готовых, целое от 0; 0 — первым |
| `id` | готовый опознаватель: так отправляет тот, кто повторяет уже рождённое сообщение |
| `timeout` | срок вызова; запись в WAL им не прерывается (см. «Чем пришлось поступиться») |

Незнакомый ключ — исключение с его именем, а не молчаливый пропуск:
обработчик, переехавший на очередь, которая чего-то не умеет, должен
упасть в проверках.

```lua
mail:send('тело', { priorty = 1 })
--> error: настройки отправки: ключа «priorty» нет, есть delay, headers, id,
--> key, priority, timeout, ttl
```

**Тело — простые данные**: `nil`, логика, конечное число, строка
и таблицы из них; ключи таблиц — строки и числа. cdata (`int64`,
`decimal`, `uuid`, `datetime`), функция, NaN, бесконечность и кольцо —
исключение при отправке с путём до негодного значения:

```lua
mail:send({ order = { total = require('decimal').new('9.90') } })
--> error: тело.order.total — простые данные, а не cdata
```

Такое тело не пережило бы ни JSON брокера, ни переезд на другую очередь
с тем же договором. Большое целое едет строкой. Одна и та же таблица
в двух ветках тела — не кольцо.

Пределы тела те же, что у всех очередей договора: **не глубже 100
таблиц** и **не больше 10 000 значений**, считая каждую ссылку на таблицу
так, как её запишет кодек. Конверт и кортеж рока кладут тело ещё на два
уровня глубже, а msgpack не пишет глубже 128 таблиц, — поэтому тело сверх
предела отвергается исключением на строке отправителя, а не отказом
`broken` уже в трубе:

```lua
local deep = {}
local node = deep

for _ = 1, 126 do
    node.next = {}
    node = node.next
end

mail:send(deep)
--> error: тело — вложенность глубже 100 таблиц
```

### Конверт

Обработчик получает таблицу:

| Поле | Что |
|---|---|
| `id` | ULID отправителя; тот же у повторной выдачи |
| `name` | имя очереди |
| `body` | тело |
| `headers` | заголовки: контекст отправителя и его собственные |
| `key` | ключ порядка или `nil` |
| `attempt` | номер выдачи: 1 на первой, растёт на каждой |
| `created` | стенное время отправки, секунды |

```lua
mail:consume(function(message)
    message.id                          --> '01K5…', 26 знаков
    message.body                        --> { to = 'a@example.org' }
    message.headers                     --> { ['x-tenant'] = 'acme' }
    message.attempt                     --> 1
end)

mail:send({ to = 'a@example.org' }, { headers = { ['x-tenant'] = 'acme' } })
```

Конверт приходит копией: правка его в обработчике ничего не меняет
в очереди.

### Получатель: `consume` и `stop`

`queue:consume(handler, opts) → consumer` заводит работников; у каждого
свой файбер с именем `queue/<имя>/<номер>`.

```lua
local consumer = mail:consume(handler, { workers = 2, max_attempts = 3 })

consumer:stop()                         -- новые сообщения не берёт
```

| Ключ | Что | Умолчание |
|---|---|---|
| `workers` | сколько обработчиков идёт разом | 1 |
| `max_attempts` | после этой выдачи неудача зарывает | 5 |
| `backoff` | отступ перед повтором: `{ base, max }`, `base · 2^(выдача−1)`, не больше `max`, секунды | `{ base = 1, max = 60 }` |
| `atomic` | запись обработчика и подтверждение — одна транзакция (см. «Транзакции `box`») | `false` |

Обработчик, который нельзя позвать, и незнакомая настройка — исключение
на строке вызывающего:

```lua
mail:consume(handler, { worker = 2 })
--> error: настройки получателя: ключа «worker» нет, есть atomic, backoff,
--> max_attempts, workers
```

`stop()` перестаёт брать новые сообщения; взятое дорабатывается.
Работник, ждущий задачи, замечает остановку не позже чем через
полсекунды. Сколько работников ещё живо — поле `consumer.workers`.

Права у обработчика — права фонового файбера, то есть процесса, а не
того, кто объявил получателя. В чужой транзакции обработчик не зовётся:
у работника свой файбер.

### Итог обработчика

Подтверждение — не вызов, который можно забыть, а то, что вернул
обработчик:

| Обработчик | Итог |
|---|---|
| вернул значение или ничего | подтвердить |
| `nil, err` либо `false, err` | вернуть с отсрочкой `err.retry_after`, иначе по отступу; выдача номер `max_attempts` — зарыть с причиной «попыток N из M: …» |
| `nil, err` с `err.retriable == false` | зарыть сразу: повтор негодного тела ничего не даст |
| бросил исключение | как отказ, причина — его текст; в журнал идёт `error` со стеком |

```lua
mail:consume(function(message)
    if message.body.to == nil then
        return nil, { retriable = false, message = 'адресата нет' }
    end

    local sent, err = smtp.send(message.body)

    if sent == nil then
        return nil, err                 -- повтор; err.retry_after, если он есть
    end
end, { max_attempts = 3, backoff = { base = 0.5, max = 30 } })
```

`err` читается по полям, а не по типу: `retriable` есть и у
`TntStorageFailure`, и у отказа
[`tnt-http`](https://github.com/tnt-skein/tnt-http), а таблица без
`retriable` и строка — повторяемый отказ. Причина в зарытом и в журнале —
поле `message` таблицы, если оно строка, иначе `tostring`: отказ-таблица
без метатаблицы иначе показалась бы адресом `table: 0x…`.

`retry_after` читается `tonumber` — числом и строкой секунд одинаково:
у отказа `tnt-http` в `retry_after` лежит заголовок `Retry-After` как
пришёл, строкой, и обработчик, вернувший такой отказ как есть, повторяется
тогда, когда просил сервер. Дата, отрицательное и NaN числом секунд
не читаются — повтор идёт по отступу; бесконечность упирается в потолок
в сто лет.

### Зарытые и возврат: `kick`

Зарытое — сообщение, которому нужен человек. Оно уходит в спейс
`<имя>_dead` одной транзакцией с подтверждением задачи:

| Поле | Что |
|---|---|
| `id` | опознаватель сообщения |
| `reason` | причина: «попыток 3 из 3: сервис недоступен» |
| `attempt` | на какой выдаче зарыто |
| `buried` | стенное время, секунды |
| `message` | конверт целиком |

```lua
box.space.mail_dead:select({}, { limit = 10 })  -- что зарыто и почему

local moved, err = mail:kick(50)        -- до пятидесяти зарытых — назад на выдачу
```

`queue:kick(count) → moved | nil, err` возвращает до `count` зарытых,
по умолчанию одно, одной транзакцией. У возвращённого счёт выдач
начинается заново. Не восстанавливаются `ttl`, отсрочка и приоритет
прежней отправки: их знает отправитель, а не зарытое. Зарытое
не выбрасывается по `ttl`: чистит его человек либо отдельная уборка.

Возврат идёт своей транзакцией, и в чужой его не зовут — это исключение.
На узле для чтения возврат отказывает `unreachable`, как и отправка.

Зарывается и то, что до обработчика не дошло:

- **не конверт** — в трубу положили мимо пакета: причина «в трубе
  не конверт tnt-queue», тело — то, что лежало в задаче;
- **выдач больше `max_attempts`** — сообщение, которое роняло процесс,
  иначе выдавалось бы после каждого перезапуска без конца: причина
  «выдач N при потолке M: прежние выдачи итога не вернули»;
- **тело не по форме**, если очередь объявлена с `shape`: причина
  «тело не по форме: …».

### Сроки: `ttr`, `ttl`, `delay`, `touch`

- `ttr` — сколько у обработчика на одно сообщение. Не уложился — очередь
  выдаёт сообщение снова, и работа делается дважды: итог первого
  опоздает, будет сосчитан (`late`) и записан `warn`.
- `ttl` — сколько сообщение живёт в очереди с отправки. Истекло — рок
  удаляет его молча, как только оно готово к выдаче; взятое доживает
  до конца `ttr`, и итог обработчика записывается, а если `ttr` вышел
  раньше итога, сообщение уже не выдаётся. Пакет ловит удаление крюком
  рока, считает `expired` и пишет `warn`. Умолчания у `ttl` нет:
  сообщение ждёт, пока его не обработают.
- `delay` — не выдавать раньше срока; возврат с отсрочкой продлевает
  и `ttl` на ту же отсрочку — так считает рок.
- Возврат без отсрочки (`retry_after = 0`, нулевой отступ) `ttl`
  не трогает: сообщение истекает в свой срок с отправки. Рок
  `queue 1.5.0` в этой ветке срок теряет, и пакет пишет его заново той же
  транзакцией.
- `queue:touch(message, seconds) → true | nil, err` — продлить `ttr`
  сообщения, которое сейчас в работе **у этого файбера**:

```lua
mail:consume(function(message)
    for _, page in ipairs(message.body.pages) do
        mail:touch(message, 30)         -- ещё полминуты на страницу
        render(page)
    end
end)
```

Из соседнего файбера продление не проходит: у рока своя сессия у каждого
файбера — отказ `rejected` с текстом рока. Сообщение, которого нет
в работе у очереди, — тоже `rejected`: «сообщение … не в работе
у очереди mail».

**Сроки рока меряются стенными часами цикла событий.** Перевод часов
назад продлевает `ttl`, `ttr` и `delay` на величину перевода, вперёд —
обрывает их. Пакет это не чинит.

### Порядок и ключ

Порядок **между** сообщениями не обещается: `workers > 1`, повтор
с отсрочкой и `delay` его ломают. Порядок **внутри ключа** обещается:
пока сообщение ключа взято, следующее того же ключа не выдаётся, даже
если работников несколько.

```lua
local orders = queue.declare('orders')

orders:consume(handler, { workers = 4 })

orders:send({ order = 11, status = 'paid' }, { key = 'o-11' })
orders:send({ order = 11, status = 'shipped' }, { key = 'o-11' })
-- второе ждёт, пока работник кончит с первым
```

Сообщение без ключа получает ключом свой опознаватель — иначе все
безключевые шли бы одной цепочкой, и `workers` ничего бы не дали.
Готовые сообщения выдаются по `priority`, при равном — по порядку
отправки.

Возврат без отсрочки ключ не отпускает: при равном `priority`
возвращённое выдаётся снова раньше следующего сообщения того же ключа.
Возврат с отсрочкой отпускает ключ на время отсрочки, и следующее
выдаётся раньше возвращённого.

`bury` порядок ключа ломает: зарытое уходит из ключа, и следующее
выдаётся раньше него. Это цена того, что ключ не стоит навечно из-за
одного негодного сообщения.

### Транзакции `box`: отправка и `atomic`

**В транзакции `box` отправка — её часть**: откат уносит и сообщение.

```lua
box.begin()
box.space.orders_paid:insert({ 2 })
mail:send({ order = 2 })
box.commit()                            -- заказ и письмо — одной фиксацией

box.begin()
box.space.orders_paid:insert({ 3 })
mail:send({ order = 3 })
box.rollback()                          -- ни строки, ни сообщения
```

Это и есть повод держать очередь в спейсе: «сохранили и поставили
работу» одной транзакцией, без ящика исходящих. Для отправки **наружу**
в той же транзакции нужен ящик исходящих
[`tnt-outbox`](https://github.com/tnt-skein/tnt-outbox): сетевой
отправитель ждал бы брокера, а уступка порвала бы транзакцию.

Обработчик с **`atomic = true`** идёт внутри `box.begin()`, а
подтверждение — последний оператор той же транзакции: запись
обработчика и подтверждение фиксируются вместе, и повтор после обрыва
невозможен.

```lua
local paid = queue.declare('paid')

paid:consume(function(message)
    box.space.receipts:insert({ message.id, message.body.order })
end, { atomic = true })
```

Обработчик в такой транзакции **не уступает**: ни сети, ни
`fiber.sleep`. Уступка после первой записи рвёт транзакцию, запись
обработчика откатывается, и это считается попыткой с причиной
«Transaction has been aborted by a fiber yield» — после `max_attempts`
сообщение зарыто, а не потеряно. Отказ `nil, err` тоже откатывает запись
обработчика.

Без `atomic` повтор отсекают отметкой опознавателя в той же транзакции,
что и запись обработчика, — модулем `tnt.outbox.inbox` пакета
[`tnt-outbox`](https://github.com/tnt-skein/tnt-outbox). Отметка
фиксируется и откатывается вместе с записью, `claim` отвечает `false`
на повтор, а старые отметки стирает уборка по сроку:

```lua
local inbox = require('tnt.outbox.inbox')
local shipped = queue.declare('shipped')

inbox.start()                           -- при подъёме узла: спейс отметок заведён

shipped:consume(function(message)
    box.atomic(function()
        if inbox.claim('shipments', message) then
            box.space.shipments:insert({ message.id, message.body.order })
        end
    end)
end)
```

[`tnt-once`](https://github.com/tnt-skein/tnt-once) для этого
не годится: он помнит 512 ключей четверть часа и в памяти, а повтор
доставки приходит и после перезапуска.

### Узел для чтения и смена ведущего

На узле для чтения очередь не принимает и не выдаёт:

```lua
local id, err = mail:send('работа')
-- nil, «очередь mail не принимает: узел только для чтения»; если труба
-- уже была заведена, в причине — состояние рока: WAITING, STARTUP
```

Отказ — род `unreachable`, `sent = false`, `retriable = true`: для
[`tnt-retry`](https://github.com/tnt-skein/tnt-retry) это обычный
повторяемый отказ. Работник в это время **ждёт записи**, а не опрашивает
очередь: цикл `take` на узле для чтения не уступает вовсе и вешает узел
целиком.

Смена ведущего проводит очередь через `STARTUP` даже на одиночном узле:
после возврата в запись узел уже пишет, а очередь ещё нет, и в это окно
отправка отвечает тем же `unreachable` с состоянием рока.

Отправка в транзакции, пока труба не заведена, отказывает тем же
`unreachable` с причиной «труба ещё не заведена»: труба — это DDL, а DDL
уступает и порвал бы транзакцию вызывающего. Такое бывает только
на узле, который только что стал писать и ещё ничего не отправлял.

Взятое на прежнем ведущем новый ведущий выдаёт снова — это и есть «хотя
бы раз».

### Контекст

Контекст отправителя едет в `headers` сообщения: отправитель кладёт
туда `context.export()` в миг отправки, поверх — свои заголовки
из `headers`, они главнее. Обработчик исполняется в области
`context.run(context.import(headers))`, и записи журнала из него несут
тот же опознаватель запроса.

```lua
local context = require('tnt.context')

mail:consume(function(message)
    context.get('request_id')           --> 'r-7'
    message.headers['x-request-id']     --> 'r-7'
end)

context.run({ request_id = 'r-7' }, function()
    mail:send({ to = 'a@example.org' })
end)
```

Без `request_id` в заголовках обработчик получает свой ULID: запись
обработчика без опознавателя в журнале не найти. Едут только ключи
контекста с объявленным заголовком (`context.declare(имя, { header = … })`)
— так до обработчика доходит и трасса, если её ключи объявлены.

### Крюки: `hook` и `hooks`

Крюк — то, что приложение добавляет к отправке и к обработке сверх
настроек вызывающего: отрезки трассы `producer` и `consumer`, замер,
своя запись. Пакет от трассировщика не зависит: знание о нём приходит
крюком.

`queue.hook(name, hook)` ставит крюк, заменяет крюк с тем же именем на
его прежнем месте или снимает его, если `hook` — `nil`. Крюк —
`hook(call, proceed)`, где `call = { kind = 'send' | 'handle', name,
message }`:

```lua
local clock = require('clock')
local took = {}

queue.hook('timing', function(call, proceed)
    local started = clock.monotonic()

    proceed()
    table.insert(took, { kind = call.kind, name = call.name, seconds = clock.monotonic() - started })
end)

queue.hooks()                           --> { 'timing' }
queue.hook('timing', nil)               -- снять
```

На отправке конверт собирается **внутри** `proceed`: заголовки несут
контекст, который завёл крюк, а `call.message` появляется после
`proceed`. На обработке конверт уже есть до крюка — из него крюк берёт
родителя трассы.

Крюки идут снаружи внутрь в порядке постановки: первый поставленный
видит обращение первым и итог последним. Замена оставляет крюк на месте:
крюк ставят и при старте, и при перечитывании настроек, и порядок
от этого меняться не должен. `proceed` исполняется один раз, его итог —
итог отправки либо обработки; что вернул сам крюк, не читается.

Сорвавшийся крюк ничего не срывает: бросивший и не позвавший `proceed`
пропускаются — `proceed` зовёт пакет сам, — и пишется `warn` с именем
крюка. Отменить отправку крюк не может: телеметрия не решает, уйдёт ли
сообщение. Список крюков — состояние процесса: очереди объявляются
внутри разных пакетов приложения, и крюк, поставленный ради одной
из них, до других всё равно дошёл бы.

### Состояние и счётчики: `status` и `features`

```lua
mail:status()
--> {
-->     name = 'mail', ttr = 30, state = 'RUNNING', workers = 2,
-->     counts = { sent = 12, ack = 10, retry = 3, bury = 1, late = 0,
-->                expired = 0, failures = 0, idle_waits = 0 },
-->     depth = { ready = 1, taken = 1, delayed = 0, dead = 1 },
-->     hooks = { 'timing' },
--> }
```

`state` — состояние рока (`RUNNING`, `WAITING`, `STARTUP`) либо `CLOSED`,
пока труба не заведена; глубина `depth` считается только у принимающей
очереди. Счётчики — с первого объявления имени, в памяти, одни у всех
его объявлений: `sent` — отправлено, `ack` — подтверждено, `retry` —
возвращено с отсрочкой, `bury` — зарыто, `late` — итог опоздал и работа
повторится, `expired` — выброшено по `ttl`,
`failures` — сбоев шага работника, `idle_waits` — сколько раз работник
ждал, пока очередь начнёт принимать. `workers` — сколько работников всех
получателей очереди ещё живо.

Что умеет очередь, видно в `queue.features`: по нему код, который
пишется и для очереди, и для шины событий, решает, какие настройки
передавать.

```lua
queue.features
--> {
-->     delay = true, ttl = true, ttr = true, touch = true, priority = true,
-->     key = true, transactional = true, atomic = true,
--> }
```

`transactional` — отправка в транзакции `box` становится её частью.

### Отказ

Отказ — пара `nil, err`, где `err` — `TntStorageFailure` из
`tnt-storage`: тот же вид, что у драйверов хранилищ, и тот же договор
с `tnt-retry`. Строкой отказ — свой текст.

| Род | Когда | `sent` | `retriable` |
|---|---|---|---|
| `unreachable` | очередь не принимает: узел для чтения, смена ведущего, труба ещё не заведена | `false` | `true` |
| `broken` | исключение рока или box при отправке и возврате зарытых | `true` | только у отправки с готовым `id` |
| `conflict` | транзакция отправки откачена: кворум синхронной репликации | `false` | `false` |
| `rejected` | продлить нечего: сообщение не в работе у этого файбера | `false` | `false` |

```lua
local id, err = mail:send('работа')

id                                      --> nil
err.kind                                --> 'unreachable'
tostring(err)                           --> 'очередь mail не принимает: узел только для чтения'
```

`broken` после отправки повторять вслепую нельзя: сообщение могло лечь.
С готовым опознавателем повтор узнаётся по нему, и `retriable` — `true`.

Исключение — ошибка программиста: незнакомая настройка, негодное имя
очереди, объявление имени с другими настройками, тело не из простых
данных, тело не по объявленной форме, возврат зарытых внутри чужой
транзакции.

### Журнал

Тело сообщения в журнал не пишется: в нём бывают персональные данные.
Пишутся имя очереди (`destination`), опознаватель, номер выдачи
и причина.

| Событие | Уровень |
|---|---|
| сообщение зарыто | `error` |
| обработчик бросил | `error` со стеком |
| итог опоздал, сообщение истекло по `ttl`, сбой шага работника, сорвавшийся крюк | `warn` |
| сообщение возвращено на выдачу | `debug` |

Сбой шага и срыв крюка пишутся с подавлением повторов: беда, которая
держится, иначе писала бы строку на каждом шаге.

### Ряды метрик

Счётчики `status()` видны и рядами в реестре встроенного `metrics`
([`tnt-metrics`](https://github.com/tnt-skein/tnt-metrics), «Прикладные
ряды»): ряд растёт в том же месте, что и счётчик, и разойтись им нечем.
Имена и метки — одни у всех очередей договора: ряды `message_*`, метка
`destination` — имя очереди. Объявляет их общая часть договора
([`tnt-message`](https://github.com/tnt-skein/tnt-message),
`tnt.message.series`): те же ряды пополняет шина событий,
и обработчик, переехавший с шины на очередь, остаётся на тех же графиках.

| Ряд | Род | Метки | Что значит |
|---|---|---|---|
| `message_sent_total` | counter | `destination` | отправлено; растёт с `counts.sent` |
| `message_send_failures_total` | counter | `destination`, `kind` | отказ отправки по роду; у очереди — `unreachable`, `broken`, `conflict` |
| `message_handled_total` | counter | `destination`, `outcome` | итог обработки: `ack`, `retry`, `bury`, `late` |
| `message_expired_total` | counter | `destination` | выброшено по `ttl` |
| `message_worker_failures_total` | counter | `destination` | сбоев шага работника |
| `message_wait_seconds` | histogram | `destination` | сколько сообщение ждало первой выдачи |
| `message_depth` | gauge | `destination`, `state` | сколько лежит: `ready`, `taken`, `delayed`, `dead` |

**Длина** — шкала со сбором: глубину у рока спрашивает каждая выкладка,
как `status().depth`, а не каждое движение сообщения. Очередь, которая
сейчас не принимает (узел для чтения, подъём), глубины не знает, и её
строк в ряду нет. В ряду — объявленные очереди: объявление держит
очередь до `queue.reset()`, забытая и никем не удерживаемая очередь
из ряда уходит сама, а объявленная заново после `reset` заменяет
прежнюю. Шкала одна на все очереди договора: глубина очереди и события
с тем же именем складывается по состоянию.

**Ожидание** — от отправки до взятия работником, на первой выдаче:
повторная выдача ждала отсрочки повтора, а не очереди. Отсрочка `delay`
в ожидание входит. Корзины — от 10 мс до часа.

**Отказы** — два ряда: отказ отправки по роду и итог обработки. `retry`,
`bury` и `late` — отказы обработчика, `message_worker_failures_total` —
поломка самой очереди. Отказ возврата зарытых в ряд отправки не идёт.

Потолок очередей в ряду — сто (`require('tnt.message.series').DESTINATIONS`):
очередь сверх него идёт словом `_other`. Как ряды выглядят в выкладке
живого узла — документ `tnt-metrics`, «Как смотреть».

### Подмена в проверках

Рок, сон работника и признаки узла — внешние зависимости, объявленные
через `tnt-external`, и подменяются `_set_source` по одному имени;
остальное остаётся настоящим.

| Модуль | Имена |
|---|---|
| `tnt.queue.tube` | `load` — загрузить рок, `writable` — пишет ли узел |
| `tnt.queue.worker` | `sleep(seconds)` — сон, `wait_rw(timeout)` — ждать записи, `read_only` — узел только для чтения |

```lua
local tube = require('tnt.queue.tube')

tube._set_source({ writable = function() return false end })

local later = queue.declare('later')
later:send('работа')                    --> nil, «очередь later не принимает: узел только для чтения»

tube._set_source(nil)                   -- настоящие средства вернулись
```

Так ветка узла для чтения проверяется без переключения узла. Работу
самой трубы подменять незачем: она чужая, и проверять её двойником
значило бы доказать, что пакет правильно разговаривает сам с собой.

## Чем пришлось поступиться

- **Четыре записи WAL на сообщение** вместо трёх: счёт выдач пишется
  сразу за взятием. Без него сообщение, роняющее процесс, выдавалось бы
  без конца.
- **Обработчик дольше `ttr` работает дважды.** Отменить файбер без
  уступки нечем; `ttr` отдаёт сообщение другому, а итог первого
  считается опоздавшим.
- **`timeout` отправки не ограничивает запись в WAL**: box своего срока
  фиксации не даёт. Настройка принимается и проверяется, но отправку
  не прерывает.
- **Счёт `sent` растёт в миг вызова**, а не фиксации: отправка,
  откаченная вместе с транзакцией вызывающего, в счётчике уже учтена.
- **Отправка в транзакции, пока труба не заведена, отказывает.** Труба —
  это DDL, а DDL уступает: завести её внутри чужой транзакции значит
  порвать транзакцию вызывающего.
- **Зарытые не видны в `queue.statistics()` рока** — только в `status()`
  пакета: цена того, что они не исчезают по `ttl`.
- **Остановка получателя занимает до полусекунды**: работник ждёт задачу
  со сроком, и отменить это ожидание рок не даёт.
- **Порядок только внутри ключа**, и зарытое из ключа уходит: следующее
  сообщение ключа выдаётся раньше него.
- **Сроки меряются стенными часами**: перевод часов сдвигает `ttl`,
  `ttr` и `delay`.
- **Сообщение, взятое в миг падения процесса, после подъёма по `ttl`
  не выбрасывается.** Такие задачи рок `queue 1.5.0` при подъёме
  возвращает сам, той же веткой без отсрочки, что теряет срок, и до пакета
  дело не доходит. До конца `ttl` сообщение выдаётся как обычно, а после —
  не выдаётся, но и не выбрасывается: лежит в `depth.ready`, и `expired`
  о нём не знает.
- **Ожидание меряется стенными часами отправителя.** Отметка `created`
  в конверте стоит по часам узла, который отправил, и после смены
  ведущего расхождение часов двух узлов входит в ожидание; отрицательное
  идёт нулём. Возвращённое `kick` зарытое на первой выдаче меряется
  от первой отправки — другой отметки у конверта нет.
- **Настройки очереди одни на процесс.** Сменить `ttr` вторым
  объявлением нельзя: срок сообщения зависел бы от того, через какое
  объявление его отправили. Новые настройки приходят с `queue.reset()`
  при перечитывании кода либо с перезапуском.
- **Работам обслуживания узла очередь не годится**: каждое движение
  задачи пишет WAL на узле, диск которого чистят, а на реплике, где
  обслуживание чаще всего и идёт, очередь не работает.
- **Обработчик вне Tarantool эту очередь не читает**: работники — файберы
  узла, и драйвера поверх Redis у пакета нет. У очереди в Redis отправка
  не была бы частью транзакции `box`, запись обработчика и подтверждение
  не легли бы одной транзакцией, и `queue.features` зависели бы
  от настройки. Чужому процессу сообщение
  уводит ящик исходящих
  [`tnt-outbox`](https://github.com/tnt-skein/tnt-outbox) одной
  транзакцией с данными, а доставляет брокер — через
  [`tnt-amqp`](https://github.com/tnt-skein/tnt-amqp) или
  [`tnt-kafka`](https://github.com/tnt-skein/tnt-kafka).

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`.
Модули пакета берутся из исходников, зависимости — установленными.

Работа внутри чужая, и проверять её двойником незачем: труба, сроки,
ключ и возврат идут против настоящего рока на временном узле Tarantool,
который luatest поднимает на время группы. Конверт, настройки отправки
и тело, приговор обработчику и крюки — общая часть договора, и проверяет
её `tnt-message`. В процессе проверок остаются настройки объявления
с их текстами отказа, повторное объявление и сверка его настроек,
`reset`, тело сверх предела на строке отправителя, чужое
содержимое трубы, запись об истёкшем сообщении и работник на двойнике
внешней зависимости: ожидание записи на узле для чтения, короткий сон
в окне подъёма, пауза после сбоя шага, стек брошенного, контекст
отправителя, имя файбера. Отказы аргументов сверяются текстом и местом:
винится строка вызывающего.

Три группы поднимают узел. Первая проверяет очередь целиком: выдачу
с контекстом, отступ и зарытые, `retriable == false` и `retry_after`,
опоздавший итог по `ttr`, порядок ключа при двух работниках, отправку
в транзакции, `atomic` с уступкой и отказом, возврат зарытых, отсрочку
и приоритет, истечение по `ttl` — и после возврата без отсрочки, —
порядок ключа при возврате без отсрочки и с ней, чужое содержимое
трубы, выдачу сверх потолка, `touch` из своего и соседнего файбера,
форму тела, сбой шага, объявление поверх чужого спейса, гонку двух
объявлений, одну очередь на два объявления — со счётом, `touch`
и истечением, — отказ заведения, не забывающий прежнее объявление,
`reset`, после которого крюк рока считает для нового объявления, и крюки
на узле.
Вторая — узел для чтения: рок не грузится, работник ждёт записи и не
занимает цикл событий, отправка в транзакции до заведения трубы,
переход узла в чтение и окно подъёма. Третья рвёт очередь: спейс трубы,
унесённый из-под рока, даёт `broken`, а откат синхронной транзакции без
кворума — `conflict`.

Ряды проверяются дважды: без узла — какой ряд растёт с каким счётчиком
очереди, глубина только у принимающей и удерживаемой очереди, — и на узле:
настоящая работа очереди доходит до рядов, глубина берётся у рока
на каждом сборе, отказы отправки видны по роду. Роды рядов, корзины
и ожидание только первой выдачи проверяет общая часть договора
(`tnt-message`).

Покрытие строк — 100 %, убитых мутантов — 100 % (58 проверок, 31 из них —
на узле).
